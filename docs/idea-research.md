# Idea research: what to build for "Build Agents That Run Code"

Compiled from four Exa-driven research passes (GitHub, past hackathons, startups, Stripe angle). Official ideas are referred to as `#N` (see [ideas.md](ideas.md)).

**Link honesty:** every URL below was returned by Exa search or fetch. The research agents did not open each page separately; star counts and prize details come from the Exa excerpts and are labelled "n/s" when not shown. Vendor claims (benchmarks, customer counts) are unverified. Links marked (unconfirmed) were seen only via a gallery or social post.

**Sandbox feature shorthand:** FORK = memory+disk fork, EGRESS = egress allowlist, URL = public HTTPS ingress, PAUSE = pause/resume + wake-on-request, DESKTOP = desktop:1 image with Chrome/computer use.

---

## Patterns that keep winning (read this first)

- **Fork is the under-served feature.** Most open-source demos fake "parallel attempts" with git worktrees. Only microVM projects (mitos, forkd, crucible) do real live forks. A CreateOS-native fork-and-race with a live scoreboard shows something most demos can't. Daytona-hackathon team FAAFO said outright that forking was unavailable on their tier.
- **Winning demos show a hard number and a near-miss pair**: "10/10 on a labelled set", "error to PR in under 64 s", the same engine allowing `rm -rf node_modules` but blocking `cat .env` then POST. Judges also rewarded honest labelling of what is mocked.
- **Self-exploit beats scripted attack** (Custodian won the Stripe/Nous hackathon partly for catching an agent rewriting its own policy file).
- **A real human user** helps (Mom-n-Pop Skills placed 2nd of 292 by building for the author's parents with human approval on every action).
- **Stripe risk:** MPP needs a Stripe profile ID; card charges have a ~$0.50 floor; Agentic Commerce Suite is gated preview. Check MPP test mode in the first 15 minutes (details in the Stripe table).

## Top 5 build candidates

Scoring: 5-hour feasibility 1 to 5 (5 = very safe). "Sandboxes" counts concurrent sandboxes needed at peak. The free plan has 1 sandbox / 1 vCPU; the Beginner plan has 5. Every candidate has a sequential fallback that works on 1 sandbox unless noted.

### 1. "Will My Webhook Survive Black Friday?": load-test and self-fix a Stripe webhook handler (feasibility 3.5/5)

- **References:** hookshelf-mcp https://github.com/vinkurov/hookshelf-mcp , Gatling AI https://gatling.io/ai , k6-loadtest-mcp https://github.com/krishanchawla/k6-loadtest-mcp , Stripe Webhook Fixer idea (#1), agentprobe https://github.com/agentprobe2026/agentprobe
- **Pitch:** Point it at a repo with a Stripe webhook handler. The agent deploys the handler in sandbox A (public URL), then writes a k6 script in sandbox B that fires signed Stripe test events: duplicates, out-of-order, burst, tampered signatures. It watches p95, error rate and duplicate side effects, finds the bug (no idempotency key, signature check on parsed JSON, slow handler timing out), patches the handler, redeploys and reruns until the numbers pass. Extends #1 with the load-testing gap that the official list doesn't cover.
- **User/problem:** Webhook bugs (double-fulfilment, dropped events) show up only in production under load; load testing needs a specialist so teams skip it.
- **Demo moment:** Before/after chart: 14% duplicate orders under burst, then 0% after the agent's idempotency patch. Live traffic graph on the public URL.
- **Sandbox features:** URL (handler + report), EGRESS (generator allowed to reach only the target; handler allowed only Stripe/DB), FORK (re-run profiles from a snapshot), PAUSE optional.
- **Stripe:** Stripe CLI/test events and signature verification (real, test mode); Stripe Projects for the stack; optional `stripe-agent-toolkit` meter events for run cost.
- **Concurrency:** Two sandboxes (target + generator). Free plan (1 sandbox) means target and k6 share a 1-vCPU box, which skews latency numbers, so use Beginner (5) or compare relative before/after only.
- **Risk:** Moderate. The signed-event firing is the main work; hookshelf-mcp shows the pattern. Need a deliberately buggy sample handler prepared in advance.

### 2. "Click Once, Ship an API": computer-use agent that turns a legacy portal into a generated API (feasibility 2.5/5)

- **References:** Parse https://www.ycombinator.com/launches/OnX-parse-apis-for-any-website , Integuru https://news.ycombinator.com/item?id=41983409 , Skyvern https://www.ycombinator.com/launches/Odo-skyvern-asking-ai-to-build-scrapers-should-be-easy-right , Webskillet https://www.ycombinator.com/launches/Rkz-webskillet-ai-web-automation-that-gets-cheaper-every-run , e2b-dev/desktop https://github.com/e2b-dev/desktop , Surf https://github.com/e2b-dev/surf , record-and-replay-skill https://github.com/ugarchance/record-and-replay-skill
- **Pitch:** Give it a portal with no API (a mock invoice portal you host) and a goal: "download my last 3 invoices". A computer-use agent does it live in the desktop sandbox while viewers watch the stream. It records the network calls, writes a Python/Playwright client, runs it, and publishes the client as an HTTPS endpoint on the sandbox URL. The second call returns in seconds with no LLM and no browser. The endpoint pauses when idle and wakes on request, and each call can be billed through Stripe (credits or MPP).
- **User/problem:** Small businesses depend on portals (utilities, suppliers, logistics) that have no API; RPA breaks whenever the site changes.
- **Demo moment:** Split screen of the desktop clicking for 60 seconds, then a curl hitting the generated endpoint and returning JSON in 800 ms. Hard number: "first run 74 s with LLM, run 2 in 0.9 s, $0".
- **Sandbox features:** DESKTOP (core), URL (the generated API), EGRESS (target domain only), PAUSE + wake-on-request (the endpoint), FORK (logged-in snapshot).
- **Stripe:** Per-call billing via Checkout credits or MPP (optional); Stripe Projects for the stack. This is the weakest Stripe tie of the five, so plan to make Stripe a visible but secondary element.
- **Concurrency:** 1 sandbox (desktop image) is enough if the mock portal runs elsewhere or in the same box; desktop images are heavier on 1 vCPU.
- **Risk:** Highest build risk: computer use is slow and flaky, and the desktop image on a 1-vCPU free plan may lag. Keep a pre-recorded fallback and a simple, controlled mock portal.

### 3. "Incident Forker": fork a live, broken service and race interventions on its real state (feasibility 3.5/5)

- **References:** ForkLab https://daytona-hacksprint-sf-jul-2026.devpost.com/project-gallery (gallery only, page unconfirmed), Multiverse https://devpost.com/software/multiverse-xgqfrp , forkd BRANCH of a live VM https://github.com/deeplethe/forkd , Collimate "fork, don't restore" https://collimate.ai/blog/fork-dont-restore , IncidentFox https://www.ycombinator.com/launches/PTU-incidentfox-the-ai-sre-who-never-drops-context , Deeptrace https://www.ycombinator.com/launches/Oob-deeptrace-ai-agents-for-on-call
- **Pitch:** A small checkout API runs in a sandbox and degrades under load (leaked DB connections, exhausted pool, a poisoned cache). When the alert hits the sandbox's public URL, the agent does not restart anything. It forks the live VM at the moment of degradation, memory included, into several copies. Each fork gets one intervention the agent wrote (raise the pool, patch the leak, evict the cache, roll back, add backpressure) and replays the same traffic. A scoreboard shows which fork recovers; the winning change is applied to the original and written up as a post-mortem. This only works because the fork carries process memory: a restart, a worktree or a fresh container loses the very state that caused the incident.
- **User/problem:** On-call engineers can't safely experiment on a sick production box, and a fresh reproduction rarely has the same in-memory state.
- **Demo moment:** p95 climbing on a live graph, then "fork x6", six panels race, one flatlines at healthy, and the original recovers. Hard number: time to recovery.
- **Sandbox features:** FORK with memory (core, and the reason this isn't generic), URL (alert webhook + dashboard), PAUSE (sleeps until the alert), EGRESS (read-only access to the DB/Stripe test API).
- **Stripe:** Stripe Projects for the stack. Make the broken service a Stripe test-mode checkout/webhook API so the incident is "payments failing", and replay Stripe test events as the traffic.
- **Concurrency:** 6 simultaneous forks needs Beginner (5 sandboxes). On the free plan run them one at a time from the same snapshot; the fork is still real, the race just isn't simultaneous.
- **Risk:** Needs a reproducible failure scenario built in advance (about an hour). Overlaps official #12/#20 in name, but the memory-state angle is what no one else on the list will use.

### 4. "Frozen Chore": the agent solves a messy-file chore once, freezes it into a script, and re-heals it when the input format changes (feasibility 4/5)

- **References:** Sanifu https://www.ycombinator.com/launches/QLn-sanifu-automate-the-repetitive-work-spreadsheets-are-used-for , Rima AI https://www.ycombinator.com/companies/rima-ai , Webskillet https://www.ycombinator.com/launches/Rkz-webskillet-ai-web-automation-that-gets-cheaper-every-run , Intuned https://www.ycombinator.com/launches/PxK-intuned-code-first-browser-automation-built-and-maintained-by-ai , Unyo https://unyo.ai/en/help/data-analysis , Lightski https://www.ycombinator.com/launches/KzL-lightski-embed-an-ai-data-scientist-in-your-app
- **Pitch:** A bookkeeper drops a messy supplier CSV and a payout export into the page. The agent writes and runs code in the sandbox until the reconciliation is correct, then freezes the code into a deterministic script served at the sandbox's public URL. From then on, new files run with no LLM call, in under a second. The twist is self-healing: when next month's file arrives with a renamed column, the script fails, the endpoint wakes the agent, the agent tests a repair on a fork of the sandbox, and only a passing repair is promoted. Competitors freeze once; the demo here is the freeze, the break, and the repair.
- **User/problem:** Finance and ops people redo cleaning and matching by hand every month, and scripts or RPA break silently when the format drifts.
- **Demo moment:** File A: agent works for 40 s and produces the reconciliation. File A again: 0.8 s, no LLM. File B (columns shuffled): fails, agent repairs live, passes. Hard number: LLM cost per run goes from about X cents to $0 after freezing.
- **Sandbox features:** URL (core), PAUSE + wake-on-request (core: the endpoint sleeps and wakes on the next file or on a failure), FORK (test the repair before promoting), EGRESS (none, files stay in the box).
- **Stripe:** Per-file billing with Stripe meter events or prepaid credits (the billing-credits docs); use a Stripe payout CSV as the sample data; Stripe Projects for the stack.
- **Concurrency:** 1 sandbox is enough (fork the repair test and delete it).
- **Risk:** Low. Pure Python, no desktop. Pick a sample dataset where the "format drift" is easy to stage.

### 5. "Cage Match": a purchasing agent in a locked sandbox vs. a malicious 402 seller (feasibility 3/5)

- **References:** Custodian (won by catching an agent rewriting its own policy) https://github.com/KeyArgo/custodian-kernel , link-cli and its prompt-injection warning https://github.com/stripe/link-cli and https://docs.stripe.com/agentic-commerce/agents/link-agent-wallet/machine-payments , Stripe Issuing for agents https://docs.stripe.com/issuing/agents , Loupe's cap and retry loop https://github.com/tpminhtam/auth0-stripe-hackathon , Stripe MPP docs https://docs.stripe.com/payments/machine/mpp
- **Pitch:** A buyer agent has a small test-mode budget (a Link spend request or an Issuing card with a hard limit) and must buy a data API from a seller over HTTP 402. The seller, running in a second sandbox, is hostile: its 402 challenge carries a prompt injection telling the agent to pay more, to read `.env`, or to post secrets to a third host. The buyer runs inside an egress-allowlisted sandbox, so only the seller and Stripe hosts resolve, and an Issuing authorization webhook (a public URL on the sandbox) declines anything over the cap. The page shows each attack attempt, which control stopped it, and the signed log. Then the audience picks an attack and tries to beat it.
- **User/problem:** Anyone giving an agent a card is exposed to injected 402 challenges and runaway spend; there is no good way to see the blast radius before shipping.
- **Demo moment:** Live attack log: "exfil to evil.test blocked by egress", "charge $400 declined by Issuing, cap $20", "legit $3 purchase succeeded". Honest labelling of what is mocked, which judges rewarded in past events.
- **Sandbox features:** EGRESS (core), URL (seller endpoint + authorization webhook + log page), FORK (replay each attack from the same snapshot), DESKTOP/PAUSE not needed.
- **Stripe:** Core: MPP/Link spend request in test mode, Issuing authorization webhooks, Stripe Projects for the stack. The strongest Stripe usage of the five besides a full MPP seller.
- **Concurrency:** 2 sandboxes (buyer and hostile seller). On the free plan the seller can run as a plain local process next to the buyer, at the cost of a weaker "separate machines" story.
- **Risk:** MPP/Issuing test mode needs checking in the first 15 minutes (Stripe profile ID; Issuing sandbox access is described as instant). If MPP is blocked, use Issuing alone for the cap and a plain 402 mock for the injection.

## Quick recommendation

- **Safest and most original:** #4 Frozen Chore (1 sandbox, pure Python, a clear freeze/break/repair demo).
- **Most distinctive fork demo:** #3 Incident Forker (needs the memory fork; build the failure scenario first).
- **Best Stripe story:** #5 Cage Match, after the 15-minute MPP/Issuing check.
- **Best idea outside the official list with a chart demo:** #1 Webhook Black Friday.
- **Flashiest but riskiest:** #2 Click Once, Ship an API.

Removed as too generic (these map directly to official ideas that most teams will pick): the reproduce-and-race bug fixer (#20/#24), the Airlock-style detonation gate (#7/#8), and the pay-per-run code API (#16). Their reference links remain in the source tables above if you want them.
